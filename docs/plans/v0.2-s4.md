# v0.2 S4: concern catalog + `fcs scan`

Goal: on an existing codebase, find how each UI concern is implemented today and turn the team's choice into
patterns. Nobody writes `patterns:` by hand. Spec: [spec-v0.2.md](../spec-v0.2.md) §5, §6a, §7. Decisions Q4 and Q7.

## Delivered

- **Catalog** (`@gwinnguyen/fcs-core` `CONCERNS`):
  - Concerns: `loading`, `text-input`, `page-title`, `breadcrumb`, `confirm`, `page-frame` (root of route files),
    `empty-state`, `error-display`, `date-format`, `money-format`, `toast`.
  - Each concern has signals and a `names` hint, so scan can tell an implementation from incidental use.
- **One matcher for lint and scan.** `walkFile` in the ESLint plugin backs both `fcs/pattern` and the scan
  collector, so what scan counts is exactly what lint enforces. `call` matchers now also match `new` expressions
  (`new Intl.NumberFormat`).
- **Variants** (deterministic, no LLM):
  - Each signal is attributed to the exported symbol that contains it. Import-level signals go to the file's
    implementing export.
  - An export becomes a **component variant** when its name (or file name) matches the concern's `names` hint and
    other files import that export. Its importers are its usages. Registry and already-locked files always qualify.
  - Signals anywhere else are **raw variants**, grouped by signature per file. A button that shows a spinner is raw
    spinner usage, not "the loading component".
  - `page-frame` variants are the default export's root element in route files.
- **Suggestion:**
  - The variant used in the most files, with the most recent change breaking ties.
  - Scan never auto-decides between two or more variants.
  - A single shared component (consistent) is adopted by `--write`.
  - A raw-only winner gets "consider extracting one".
- **Scopes:**
  - Counts are shown per contract scope. When the contract has none, scan derives areas from App Router route groups.
  - When each area uses exactly one variant and at least 80% of usages sit inside areas, scan suggests
    `--decide <concern>@<area>=X`. `--write` adds the area as a scope.
- **`--write`** (human-only):
  - Writes the patterns (YAML layout kept) and records a decision.
  - Runs `fcs build`, which locks the canonical components. A helper in a shared module (more than one export) gets
    `lock: false`.
  - Baselines existing usages of the losing variants.

## Validation on a real codebase

shadcn-ui/taxonomy (131 files), checked by hand:

- **date-format:** `formatDate` from `@/lib/utils`, 5 files, consistent. Correct.
- **page-title:** split by area. Dashboard uses `DashboardHeader`, docs uses `DocsPageHeader`, auth and marketing use
  a raw `<h1>`. Correct.
- **loading:** `Icons.spinner` + `animate-spin` hand-rolled in 6 components, `CardSkeleton` in dashboard
  `loading.tsx`, raw `Skeleton` elsewhere. Correct.

After `--decide page-title@dashboard=B --decide page-title@docs=C --decide loading@dashboard=C --write`:

- `fcs check` is green;
- a new dashboard file using a raw `Skeleton` is rejected with "Use <CardSkeleton>".

## Known limits

- Variants are found from code signatures only. Hand-built markup that merely looks different needs the phase 2
  visual audit.
- The `names` hint is heuristic. If a component implements a concern under an unrelated name, declare the pattern by
  hand.
