# v0.2 S3: baseline for existing code

Goal: fcs can be adopted on a running codebase without turning CI red on day one, and without turning every one-line
agent edit into a refactor. Spec: [spec-v0.2.md](../spec-v0.2.md) §4.2. Decision Q3 (nudge, don't block).

## Delivered

- **`fcs baseline [--reason]`** (human-only, like `fcs lock`) writes `.design/baseline.json`: file → violation key →
  count, plus a decision record. The key is the lint rule, refined by pattern id for `fcs/pattern(<id>)`, so an
  accepted loading violation cannot hide a new page-frame one. Parse errors are never baselined.
- **`fcs check`** reports only violations over the baseline. When a file's count for a key grows, every occurrence is
  reported, annotated with the allowance, because which one is new cannot be told. `--no-baseline` shows everything.
- **Ratchet:** full checks (`fcs check`, the Stop hook) lower counts that dropped and remove fixed files. A
  violation that was fixed cannot come back. The post-edit hook (lint-only) never rewrites the baseline.
- **Hooks:**
  - **PostToolUse:** new violations block (exit 2). Baselined ones produce a non-blocking `additionalContext` note
    (Claude Code and Codex): optional to fix, don't refactor unrelated code.
  - **PreToolUse:** blocks agent edits to `.design/baseline.json`.

Typical adoption:

```sh
npx fcs init --claude --codex
# declare patterns (or `fcs scan`, S4)
npx fcs build
npx fcs baseline --reason "adopting fcs on the existing app"
npx fcs check   # green; CI gate from now on
```
