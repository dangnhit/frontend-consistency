# v0.2 S2: lock project components

Goal: the components a project's patterns name, plus any other file the team chooses, cannot be changed by an agent
to fit one screen. People still change them on purpose, and each change is recorded.
Spec: [spec-v0.2.md](../spec-v0.2.md) §3 (lock), §4.3.

## Delivered

- **`.design/lock.json` gains `project`** (path → sha256). Project-owned locks sit beside the registry `files`. The
  legacy `ejected` map is still read.
- **`fcs build` locks canonical components.** These are the files that the `use` / `root` refs of patterns with
  `lock: true` (the default) resolve to inside the project.
  - `build` only adds locks; it never re-hashes a changed file.
  - `fcs check` reports a canonical component that is not locked, and any locked file whose content changed.
- **Commands** (each records a decision in `.design/decisions/`):
  - `fcs lock <file…> [--reason]`
  - `fcs lock --update <file…> --reason` accepts a deliberate human edit.
  - `fcs unlock <file…> --reason`. Canonical components are refused: set `lock: false` on the pattern instead.
  - `fcs eject <component…> --reason` moves a registry component under project ownership. The file stays in place
    and stays locked against agents.
- **Human-only.** `lock`, `unlock` and `eject` refuse to run without an interactive terminal, unless
  `FCS_ALLOW_NONINTERACTIVE=1`. An agent's shell cannot take a lock off to get past the hook.
- **PreToolUse hook** blocks edits to every locked file, not only `components/fcs/**`. The message tells the agent to
  use the component as-is or ask the user.
- **`fcs add`** keeps ejected files when shadcn overwrites them.
- **Agent context** says: never edit locked files, never run `lock` / `unlock` / `eject`.
